# 문서 간 관계 (Document Relationship)

5개 원본 문서가 서로 어떤 관계인지 정리한다.

특히 아래의 예상 구조가 실제 문서에 근거하여 성립하는지 확인한다.

```
ISMS-P 인증기준
→ 세부점검항목
→ 확인사항/결함사례/증적
→ 기술적 점검 기준
→ 시스템 기술점검
```

## 결론 요약

실제 문서 구조는 위의 **단일 직렬 구조와 정확히 일치하지 않는다.** 문서는 크게 두 계열로 나뉘며, 두 계열은 "인증기준 체계"와 "기술적 점검 방법론"이라는 서로 다른 성격을 갖는다.

1. **ISMS-P 계열** (안내서 + 세부점검항목 3종) — "무엇을 관리·이행해야 하는가"(요구사항/확인사항)를 규정.
2. **KISA 기술적 취약점 계열** (상세가이드) — "기술적 취약점을 어떻게 점검하는가"(점검 방법/판단 기준)를 규정.

두 계열은 **제도상 서로 다른 목적**을 가지며, KISA 가이드의 점검 결과(양호/취약)가 곧 ISMS-P 인증 결과를 의미하지 않는다.

---

## 1. ISMS-P 계열 내부 관계

### 안내서 ↔ 세부점검항목 (본인증)

- **안내서**는 인증기준을 상세 해설하는 문서이고, **세부점검항목(본인증)**은 인증기준을 표(체크리스트) 형태로 재구성한 문서다.
- 두 문서 모두 3개 영역(관리체계 수립·운영 / 보호대책 / 개인정보 처리단계별) 구조를 공유하며, 인증기준 번호(예: 2.1.1, 2.9.1)가 동일하게 사용된다.
- 세부점검항목의 "상세내용"은 안내서의 "인증기준" 문구와 대응하고, "주요 확인사항"은 안내서의 "주요 확인사항"과 대응한다.

> 출처 근거:
> - 안내서 제1장: 3개 영역 / 101개 인증기준 (ISMS 80개, ISMS-P 101개)
> - 세부점검항목 본인증 시트 1: "1. 관리체계 수립 및 운영(16개)/세부항목(42개)", "2. 보호대책 요구사항(64개)/세부항목(195개)", "3. 개인정보 처리단계별 요구사항(21개)/세부항목(91개)"

### 안내서 내부: "확인사항/결함사례/증적"의 위치

- 확인사항·결함사례·증적은 **세부점검항목(xlsx)에는 없고**, **안내서(PDF)**의 각 항목에 포함되어 있다.
- 안내서 각 항목의 구성 순서: 인증기준 → 주요 확인사항 → 관련 법규 → 세부 설명 → **증거자료 예시** → **결함사례**.
- 따라서 "확인사항/결함사례/증적"은 별도의 문서가 아니라 **안내서 내 항목별 하위 절**로 존재한다.

> 주의: 세부점검항목 xlsx의 컬럼은 `분야 / 항목 / 항목번호 / 항목명 / 상세내용 / 주요 확인사항`까지이며,
> **결함사례·증거자료 컬럼은 존재하지 않음**을 실제로 확인했다.

### 간편인증 세부점검항목(7의2, 7의3)과 본인증의 관계

- 3종의 세부점검항목은 **동일한 시트/컬럼 구조**를 사용하나, 적용 범위(분야·항목 수)가 다르다.

| 구분 | 관리체계 | 보호대책 | 개인정보 | 합계(기준) | 합계(세부항목) |
| --- | --- | --- | --- | --- | --- |
| 본인증 | 16개 | 64개(12분야) | 21개 | 101개 | 328개 |
| 7의2 | 8개 | 33개(10분야) | 21개 | 62개 | 232개 |
| 7의3 | 11개 | 33개(11분야) | 21개 | 65개 | 222개 |

- 7의2는 보호대책에서 "정책·조직·자산 관리"와 "재해복구" 분야가 빠지고, 7의3은 "재해복구" 분야만 빠진다.
- 간편인증은 보호대책 분야 번호가 재부여된다(예: 7의2에서 2.1 = 인적 보안).

> 해석: "7의2"/"7의3"이 지칭하는 고시 조문(제7조의2, 제7조의3)은 원본 고시가 없어 정확히 확인하지 못했다.
> 파일명과 범위 차이만을 사실로 기록한다.

## 2. ISMS-P 계열 ↔ KISA 기술적 취약점 계열 관계

### 두 계열은 목적과 성격이 다르다

| 구분 | ISMS-P 인증기준/세부점검항목 | KISA 기술적 취약점 상세가이드 |
| --- | --- | --- |
| 성격 | 관리체계·보호대책 **요구사항** | **기술적 점검 방법론** |
| 대상 | ISMS-P 인증 신청기관 | 주요정보통신기반시설 |
| 기준 단위 | 인증기준(2.5.1 등) | 점검 항목코드(U-01 등) |
| 판단 | 확인사항 충족 여부(심사) | 양호/취약 |

### 실제 연결 지점

ISMS-P 인증기준 중 **"취약점 점검"을 요구하는 항목**이 KISA 가이드의 점검 방법론과 연결될 수 있다.

예) 안내서 2.11.2 "취약점 점검 및 조치" 인증기준:

> "정보시스템의 취약점이 노출되어 있는지를 확인하기 위하여 정기적으로 취약점 점검을 수행하고,
> 발견된 취약점에 대해서는 신속하게 조치하여야 한다."

- 안내서 2.11.2의 세부 설명에서 "취약점 점검 대상"으로 **"서버 OS 보안 설정 취약점"**을 명시하고 있다.
- KISA 상세가이드의 "Unix 서버" 장은 바로 이 "서버 OS 보안 설정 취약점"을 **기술적으로 어떻게 점검할지**에 대한 참조 방법론에 해당한다.

### 중요한 구분 (프로젝트 원칙 재확인)

- KISA 가이드의 점검 항목은 **주요정보통신기반시설**에 대한 기술적 취약점 분석·평가용이다.
- ISMS-P 인증기준은 이와 별개의 인증 제도다.
- 따라서 **KISA 점검의 양호(취약 없음)가 곧 ISMS-P 인증기준 충족을 의미하지 않는다.**
  - 예: KISA U-01(root 원격접속 제한)이 "양호"여도, ISMS-P 2.5.5(특수 계정 및 권한관리)는 계정 관리 절차·승인·이력 등 관리적 증거까지 요구한다.
- KISA 가이드는 ISMS-P 심사에서 "취약점 점검을 수행했다"는 **수행 근거/방법**으로 활용될 수 있으나, 그 자체가 ISMS-P 인증기준을 대체하지는 않는다.

## 3. 실제 구조 정리

원본 문서에 근거한 실제 관계는 다음과 같다.

```
[ISMS-P 계열 - 인증기준 체계]
  ISMS-P 인증기준 안내서 (PDF)
    └─ 항목별: 인증기준 → 주요 확인사항 → 세부 설명 → 증거자료 예시 → 결함사례
  ISMS-P 인증기준 세부점검항목 (xlsx, 본인증)
    └─ 분야 → 항목 → 상세내용 → 주요 확인사항   (안내서의 표 재구성)
  ISMS-P 간편인증 세부점검항목 (xlsx, 7의2/7의3)
    └─ 동일 구조, 축소된 범위

[KISA 계열 - 기술적 점검 방법론]
  기술적 취약점 분석·평가 방법 상세가이드 (PDF)
    └─ 시스템 유형별(Unix/Windows/...) → 분야별 → 항목코드별
         개요 → 판단기준(양호/취약) → 조치방법 → OS별 점검·조치 사례

[느슨한 연결]
  ISMS-P 2.11.2 "취약점 점검 및 조치" (취약점 점검 수행 요구)
    ── 참조 방법론으로 ──> KISA 상세가이드 "서버 OS 보안 설정 취약점" 점검 항목
```

### 예상 구조와의 차이

- "인증기준 → 세부점검항목 → 확인사항/결함사례/증적"은 **ISMS-P 계열 내부**에서 성립한다.
- "→ 기술적 점검 기준 → 시스템 기술점검"은 **별도 계열(KISA 가이드)**이며, ISMS-P 세부점검항목의 하위 단계가 아니다.
- 두 계열 간에는 문서상 **명시적 상호참조나 항목 간 1:1 매핑이 존재하지 않는다.** 연결은 "취약점 점검"이라는 개념적 요구사항을 매개로 하는 느슨한 관계다.
